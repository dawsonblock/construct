# v0.4.1 Upgrade Gate — Authority Repair

The first repair release. No new product features. It closes the control
failure at the root of v0.3: every financial mutation now consumes a
**server-derived human actor**, never a caller-supplied `user_id`.

## What changed

### Identity (item 2)
- New `construction_ai/auth/` package: `models`, `identity`, `sessions`,
  `authorization`, `permissions`, `provisioning`.
- Identity flow: `provider_subject -> user -> organization -> AuthenticatedActor`.
  The server resolves a credential via an identity provider and issues a
  server-side session. The caller never chooses a user_id.
- `DevIdentityProvider` is the offline provider for development and tests
  (`CONSTRUCT_AUTH_PROVIDER=dev`). OIDC is the production provider
  (`CONSTRUCT_AUTH_PROVIDER=oidc`); its wiring lands with the production auth
  deploy and fails closed until then.

### Authorization (items 3, 4)
- RBAC with **DENY by default**: `roles`, `permissions` (catalog),
  `role_permissions`, `user_roles`.
- `approval_authorities`: per-user amount / currency / project limits. NULL
  `maximum_amount` means unlimited. A CAD authority does not authorize a USD
  invoice.
- Separation of duties: `creator != approver` is enforced on every approval.
  A configurable `dual_approval_threshold` requires a second *distinct*
  approver above an amount (rule implemented; full multi-signature
  accumulation lands with the invoice state machine).

### Atomic approval (items 17, 18)
- `construction_ai/approvals/service.py` `decide_approval` runs in one
  PostgreSQL transaction: `SELECT FOR UPDATE` -> validate state, actor,
  permission, authority, SoD -> `UPDATE approval` -> `INSERT approval_decision`
  -> append audit -> commit. Invariant: a committed decision always has a
  matching audit event and `approval_decisions` row.
- `approval_decisions` is append-only history; `actor_id` is a real FK to
  `users`. `approvals.decided_by` is now a denormalized display snapshot.

### API
- `POST /auth/session` exchanges a credential for a session token.
- Approval endpoints (`/approvals/{id}/approve|hold|reject`) require
  `Authorization: Bearer <session>` (resolved to an `AuthenticatedActor`) and
  accept only `{reason}`, never `user_id`.
- The org API key still authenticates non-financial endpoints (ingest, reads,
  jobs). `current_scope` (org) and `current_actor` (human) are the two identity
  dependencies.

## Schema (migrations 007, 008)

`007_authority.sql` adds: `permissions`, `users`, `identity_bindings`,
`roles`, `role_permissions`, `user_roles`, `approval_authorities`, `sessions`,
`approval_decisions`. All tenant-owned tables are ENABLE + FORCE RLS with the
same policy as 003. `identity_bindings` and `permissions` are deliberately not
under RLS (pre-scope lookup / global catalog), mirroring
`organization_api_keys`.

`008_identity_bindings_grants.sql` grants the app role write access to
`identity_bindings` (the binding write happens after a user is created, in app
context).

## What is intentionally still out of scope

- Invoice lifecycle state machine (item 5) — the approval state machine is
  formalized; the full INGESTED..FAILED invoice state machine is the next
  release.
- Relationship-decide endpoint still takes a caller `user_id`; graph
  relationship authority is item 30 (v0.4.6).
- Append-only audit role hardening, CSP, web UI session cookies — item 21
  (v0.4.3). The web UI was updated minimally to use `/auth/session` so the
  endpoint change does not break it.
- Full dual-signature accumulation (requires the state machine).
